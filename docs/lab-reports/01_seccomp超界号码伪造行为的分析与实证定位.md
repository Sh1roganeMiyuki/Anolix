# 01_seccomp 超界号码返回 38：一次根因定位

> 研究文档系列 01 ｜ 2026-09-22
> 项目：Anolix（轻量沙箱运行时核心，Go + runc）
> 环境：WSL2 Ubuntu / 内核 6.18 / runc 1.3.4 / libseccomp 2.5.5。本文所有数字与输出均来自本机真实运行，无推断值。

---

## 背景

为掌握容器运行时的**隔离与策略执行（enforcement）原理**——而不是停在"会用 Docker"的层面——我从零实现了一个轻量沙箱运行时 **Anolix**。它不做隔离本体（那是内核与 runc 的职责），只做三件事：**策略解析 → 翻译成 OCI 配置 → 管理容器生命周期**。定位是一套"可观测、可证伪"的沙箱外壳：

- **可观测**：每一次系统调用被拦截、被放行、返回值是什么，都能拿到一手证据；
- **可证伪**：任何"策略已生效"的结论都必须由实验测出，而不是看配置声明。

技术选型：Go 实现外壳（`config` 策略解析 / `launcher` OCI 生成与生命周期 / CLI），`runc 1.3.4` 作 OCI 运行时，`runtime-spec v1.2.1` 对齐仓内规范，无其它外部依赖。

### 基线一：启动链路

```
anolix run --policy examples/policy.json --rootfs ./rootfs -- /probe
   │
   ├─ config：   policy JSON（seccomp 开关 / errnoRet / 默认动作 / 放行名单）→ 严格校验
   ├─ launcher： 生成 OCI bundle（config.json）→ exec runc run → 透传退出码
   └─ 生命周期： 超时/中断先 SIGTERM 转发，兜底强杀 + runc delete 清理
```

沙箱基线（由 launcher 生成的 OCI spec 固化）：独立 pid/net/ipc/uts/mount/cgroup namespace；能力集清空 + NoNewPrivileges；seccomp 默认拒绝 + 白名单。非 root 用户下自动启用 rootless（user namespace + uid/gid 单映射 + devpts gid 适配），无需 sudo。

### 基线二：rootfs 的极简化

容器内没有动态链接器，程序必须静态编译（`CGO_ENABLED=0`）——否则会报容易误判的 `no such file or directory`（文件在，是找不到链接器）。因此 rootfs 被简化到最小：

```
rootfs/
├── probe    ← 静态 Go 探针（自检沙箱环境）
├── sysc     ← 系统调用探针（按号码传参）
└── tmp/     ← 1777 可写目录（容器 root 无 CAP_DAC_OVERRIDE，需要标准可写区）
```

没有 busybox、没有 libc——"向沙箱注入程序"的本质就是往这个目录放文件，这是唯一通道。

### 构建期的两次故障

**故障 A：runc 拒绝符号链接形式的 rootfs。**

最初实现把 `bundle/rootfs` 做成符号链接指向真实 rootfs，运行直接失败：

```
ERRO runc run failed: invalid rootfs: not an absolute path, or a symlink
```

定位到 `libcontainer/configs/validate/validator.go`：该校验要求 `filepath.Clean(path) == EvalSymlinks(Abs(path))`，即必须为规范化绝对路径、全链路无符号链接。修复见下文「修复」一节。

**故障 B：自定义白名单下容器 init 启动失败。**

裁剪白名单后容器无法启动，报错信息有误导性：

```
ensure /proc/... is on procfs: function not implemented
container process is already dead
```

原因：runc init 与容器内 Go runtime 在过滤器装载后自身仍会调用若干系统调用（实测必需：`fstatfs`、`fcntl`、`eventfd2`、`unlinkat` 等），白名单只覆盖业务代码所需调用时，这些 runtime 内部调用被拦。当时策略 `errnoRet=38 (ENOSYS)`，返回值看起来像"内核不支持"，排查一度被引向"WSL2 内核缺特性"。

> 这次故障引出了本文的核心问题：**seccomp 拦截返回的错误码，可能与其它来源的错误码取值相同。**

---

## 问题

沙箱跑起来后验证 seccomp 策略，观察到一组 errno 现象，其中三条与预期不符：

| 观察到的现象 | 与预期的偏差 |
| :--- | :--- |
| `170 sethostname` 在宿主与沙箱都返回 1 | 预期"沙箱的 1 来自策略"，但宿主的 1 与它无法区分 |
| `174`（表内空槽）宿主返回 38，沙箱也返回 38 | 同一个数字有两个来源 |
| `9999` 在两个策略（errnoRet=1 / 1145）下都返回 38 | 预期拦截码随 errnoRet 变化，实际不受配置影响 |

`9999` 最反常：按"拦截返回值随 errnoRet 变化"的规律，它本应返回 1 / 1145。本篇要回答的是：**这个 38 从哪来，谁写的。**

---

## 分析

### 实验一：三世界 errno 对照

- **预期**：沙箱内被拦调用的返回值应完全跟随策略 `errnoRet`；宿主返回值反映内核天然行为。

- **装置**：按号码传参的探针 `sysc`——第一个参数是系统调用号码（进 `rax`），后面最多六个参数（进 `rdi/rsi/rdx/r10/r8/r9`），即 x86-64 syscall ABI 的直接映射：

  ```
  ./sysc 41 2 1 0        # socket(AF_INET, SOCK_STREAM, 0)
  ```

  同一份探针在三个世界各跑一遍：**宿主**（无过滤器）／**沙箱+默认策略**（errnoRet=1）／**沙箱+example 策略**（errnoRet=1145）。

- **数据**：

| 号码（场景） | 宿主（无过滤器） | 默认策略（errnoRet=1，M=439） | example 策略（errnoRet=1145，M=435） |
| :--- | :--- | :--- | :--- |
| `41` socket（名单外） | 成功 fd=4 | 1 (EPERM) | 1145 |
| `170` sethostname（名单外） | 1（天然 EPERM） | 1 | 1145 |
| `174` 表内空槽（名单外） | 38（天然 ENOSYS） | 1 | 1145 |
| `436` close_range（默认名单内） | 0（成功） | 0 | 38 |
| `439` faccessat2（默认名单内） | — | 14 (EFAULT，放行后天然) | — |
| `440` process_madvise | 9 (EBADF) | 38 | — |
| `9999`（表外） | 38 | 38 | 38 |

- **结果**：两个发现。
  1. **错误码会重复**：`170` 在宿主天然返回 1（无权限改主机名），与沙箱策略返回的 1 取值完全相同——只看 errno 无法区分"被策略拦截"还是"没有权限"。`174` 更需注意：宿主天然返回 38（系统调用表空槽），而沙箱中超界号码被伪造的返回值也是 38。
  2. **拦截返回的错误码由策略决定**：`41` 在两个策略下分别返回 1 和 1145，数字跟随 `errnoRet` 配置——证明拦截无误，且"返回什么码"来自策略配置。

> 留一个尾巴：`9999` 不跟随配置，说明它的 38 不来自策略。来源待定位。

### 实验二：哨兵 errno 与边界扫描

- **预期**：若"拦截码随 errnoRet"成立，则应存在一个号码边界，跨过它之后返回值不再由策略决定。

- **动作一（哨兵）**：选定一个正常 errno 范围内不可能出现的数字作策略返回值——`errnoRet = 1145`。依据：真实 errno 上限 **133**，seccomp 错误码数据域上限 **4095**；取此区间内的值，任何一次观测到 1145 即可**单次确认**"这是 seccomp 拦截"，不再需要对照实验。（此前 example 曾用 38 演示 ENOSYS 伪造——这正是实验一中 38 重复的来源。）

- **动作二（边界扫描）**：对两个策略分别扫描，找到行为切换点。

- **数据**：

| 策略 | 放行名单最大号 M | M 点行为 | M+1 点行为 |
| :--- | :--- | :--- | :--- |
| 默认 | 439（faccessat2） | 439 → 14（名单内，放行后天然） | 440 → 38 |
| example | 435（clone3） | 435 → 22（放行后天然 EINVAL） | 436 → 38 |

- **结果**：存在一个动态边界 **M = 放行名单最大号**；`nr > M` 的调用一律返回 38，与 `errnoRet` 配置无关。

### 实验三：反例 440（判定 38 是伪造的）

- **预期**：若沙箱里的 38 是"内核不支持"的真实结果，那么内核明明支持的调用不可能得到 38。

- **数据**：`440`（process_madvise）宿主返回 **9 (EBADF)**——说明内核支持它且执行到了（fd 非法才报 EBADF）；但默认沙箱（M=439）里它返回 **38**。

- **结果**：超界号码返回的 38 是**伪造的**，不是内核的真实结果。

### 实验四：手写 BPF 白盒对照（定位伪造者）

- **预期**：两个待排除的假设——
  - **假设 A**：内核不把"表外号码"（如 9999）交给 seccomp 过滤器，38 是内核直接退的；
  - **假设 B**：过滤器看得见一切号码，超界 38 是生成过滤器的库（runc 所用的 libseccomp）内建写入的。

- **装置**：引入一个行为完全已知的白盒对照组——用 raw `sock_filter` 指令手写一个极简 seccomp BPF 过滤器（不经 libseccomp）：只放行 12 个程序自身运行必需的系统调用（write/exit/futex 等，供程序自己打印与退出），其余一切号码——无论是否超出内核系统调用表——一律返回特征值 `ERRNO(1234)`。

- **数据**：

  ```
  手写 seccomp 过滤器已安装（非 libseccomp）；盖章值 = 1234
    nr=39    → 被盖章: errno=1234（过滤器看得见这个号码）
    nr=170   → 被盖章: errno=1234（过滤器看得见这个号码）
    nr=174   → 被盖章: errno=1234（过滤器看得见这个号码）
    nr=9999  → 被盖章: errno=1234（过滤器看得见这个号码）
  ```

- **结果**：`9999` 被成功拦截并返回 1234，该值完全由过滤器内容决定。
  1. **推翻假设 A**：内核会把任何号码（含表外）交给过滤器——"表外号码过滤器看不见"不成立；
  2. **假设 B 成立**：判决完全由过滤器内容决定（1234/38 随写者），而沙箱里超界号码的 38 又随 M 边界精确切换——"超界 → ENOSYS"只能是 **libseccomp 编译过滤器时的内建行为**。

- **为什么 libseccomp 要伪造 ENOSYS**：编译时的已知条件是规则集只覆盖到 M，对 M 以上的号码没有用户规则可依据。此时套用用户的 default action 后果更严重（配 EPERM 会破坏程序对新系统调用的兼容性探测——glibc 的 clone3 曾因此出问题；配 KILL 会直接终止进程）。返回 ENOSYS（表示此调用不存在）是对未知号码最安全的处理，与 runc 社区"未知 syscall 应返回 ENOSYS"（issue #2151）的方向一致。

## 修复

| 问题 | 改动 |
| :--- | :--- |
| 故障 A：rootfs 被拒 | 不建符号链接；rootfs 经 `EvalSymlinks` 解析后，把真实绝对路径直接写入 OCI `root.path` |
| 故障 B：init 被自家过滤器拦 | 白名单补 runtime 必需调用（`fstatfs`/`fcntl`/`eventfd2`/`unlinkat` 等） |
| errno 无法区分来源 | 策略 `errnoRet` 由 38 改为哨兵 **1145** |

## 数据对比

| 指标 | 改前（errnoRet=38） | 改后（errnoRet=1145） |
| :--- | :--- | :--- |
| 名单外调用的返回值 | 38（与宿主"表内空槽/表外号码"的天然 38 撞值） | 1145（内核造不出，无撞值） |
| 判定"是否被策略拦截" | 需要对照实验 | 单次观测即可 |
| 超界号码（nr>M）的返回值 | 38（libseccomp 内建） | 38（同上，改 errnoRet 无效） |

## 结论与启示

### 1. 三档决策模型（最终版）

```
                       调用号码 nr
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
    nr ∈ 名单?           nr ≤ M ?              nr > M ?
        │是                 │是（不在名单）       │是
        ▼                   ▼                   ▼
     【放行】           【策略返回】          【库伪造】
    内核真执行          errnoRet=1145        ENOSYS(38)（libseccomp 内建）
    （天然结果）        【项目可配】          【改 errnoRet 无效】
```

沙箱内 errno 的三种来源：**放行 = 内核天然结果；≤M 拦截 = 策略配置的 errnoRet；>M = libseccomp 内建的伪造值**。同一个 38，在宿主上来自内核"查无此号"，在沙箱里来自 libseccomp 伪造——数字相同，来源不同。

### 2. 三层来源归属

```
【内核】seccomp 机制    = 钩子 + 忠实执行 BPF 判决（不认识号码对错）
【库】  libseccomp      = 把规则集编译成 BPF（黑盒出处：超界伪 ENOSYS 写在这里）
【项目】policy.json     = 规则内容（errnoRet / 名单），经 runc 递交给 libseccomp
```

### 3. 方法论

1. **差分对照**：单一环境的观测不足以定位（1/38 会重复）——宿主 vs 沙箱、跨策略对照、边界扫描（M/M+1）三项对照；
2. **哨兵化**：选取"只有本策略能产生的数字"（133 < x < 4095），实现单次观测即可确认；
3. **白盒对照组**：为排除嫌疑，构造行为完全已知的替代品（手写 BPF）——实验的价值在于它能推翻你自己的假设；
4. **来源标注**：每个结论标明【内核固定】/【库行为】/【项目自定义】，责任边界清晰。

### 4. 教训

- **拦截错误码的可观测性必须在策略设计时就考虑**：EPERM/ENOSYS 这类常见码会与天然错误取值相同，把调试引向错误方向；
- **"结果相同"不等于"来源相同"**：9999 的 38 在两处同值却因果链完全不同，判据是"判决发生在过滤器层还是内核表层"；
- **超界号码是策略边界（M）的函数**：删改放行名单会连锁改变其他号码的返回值——这是放行名单最大值的隐性耦合，已在本机实测确认。
