# 07_启动开销实测：4ms 与 15ms 的分段账

> 环境：WSL2 Ubuntu / 内核 6.18 / runc 1.3.4 / Go 1.27.1
> 采样：每条路径先跑 3 次热身，再计 30 次，取 p50
>
> **一句话结论**：同一台机器、同一个 payload、同一个终点，runc 路径 **15.0 ms**、zygote 路径 **4.4 ms**。但真正反直觉的是——**runc 那 15ms 几乎不随容器配置变化**：把 38 次 mount 和 159 条 seccomp 全砍掉，它还是 14.85ms。

---

## 背景

06 篇把三件围栏（cgroup / seccomp / rootfs）接进了 zygote，给足了"能跑、能执法"的证据。但有个问题始终没正面回答：

> **快多少？**

此前所有时间数字都来自 03 篇的 strace 记录，而 03 篇自己就标了"这是 strace 之下的数字，只能当上界"。拿上界去和裸跑比，比出来的倍数是假的。

所以这一篇做两件事：

1. 把 **strace 的税量化**出来——不是"慢一点"，是每条 syscall 交 40µs；
2. 用**控制变量**的方式重新量两条路径，并记录三个推翻预期的结果。

---

## 问题

要回答"zygote 比 runc 快多少"，得先解决三个坑：

| 坑 | 具体表现 |
| --- | --- |
| **终点不一致** | runc 侧容易量成"容器退出"（含 payload 运行 + 收尾）；zygote 侧容易量成"execve 返回"。两者差好几毫秒 |
| **起点不一致** | 在 shell 里 `time` 会把 fork+exec 算进去；在代码里取又容易取晚，把自身启动漏在外面 |
| **功能不一致** | runc 默认做 38 次 mount（6 基础 + 11 掩蔽 + 6 只读 + bind）+ 159 条 seccomp；zygote 一开始只挂 `/proc` 和 `/dev`。**做的事都不一样，比时间没有意义** |
| **环境不一致** | WSL 的 PATH 有 61 个目录（其中 31 个在 `/mnt/c`），rootless runc 的 `LookPath` 要跳 drvfs 搜一圈，凭空多出 60ms |

---

## 分析

### 实验一：把终点钉在同一个瞬间

新增一个最小 payload `cmd/tprobe`：它一进入 `main` 就读一次 `CLOCK_MONOTONIC`，打印相对起点的纳秒数，然后立刻退出。

**为什么不能用 `time` 量总时长**：`execve runc → execve payload` 这一段被包在 runc 内部，外面看不见。只有让 payload 自己报时，才能把两条路径的终点切在同一个瞬间——**payload 的第一条用户态指令**。

起点由父进程取、经环境变量注入：

```
runc 路径：  anolix main 取 t0 ──注入容器 env──► /tprobe 读 ANOLIX_T0_NS
zygote 路径：spawn 客户端取 t0 ──协议 T0NS──► 母体 ──env──► worker-init ──► /tprobe
```

两边的 t0 都取在"参数解析完成"之后，口径一致；两边的 payload 都是同一个静态二进制，Go runtime 初始化那点偏差也一致。

> 为什么必须用 `CLOCK_MONOTONIC` 而不是 `time.Now()`：后者的单调部分只在进程内有效，跨不了 `execve`。`CLOCK_MONOTONIC` 是系统级时钟，母体和 worker 读到的是同一根时间轴。

### 实验二：把功能档位对齐

给两侧都加"档位开关"，让它们能跑同一份工作量：

| 档位 | runc 侧 | zygote 侧 |
| --- | --- | --- |
| **最小** | `--minimal-rootfs`：只留 `/proc` + `/dev`，`MaskedPaths`/`ReadonlyPaths` 清空 | 默认：只挂 `/proc` + `/dev` |
| **完整** | 默认 spec：6 项基础挂载 + 11 条掩蔽 + 6 条只读 | `--harden`：补 4 项基础挂载 + 11 条掩蔽 + 6 条只读 |

### 实验三：逐项剥离，找瓶颈

从完整档出发，一次砍一项，看时间掉不掉：

1. 砍 mount（→ 最小档）
2. 砍 seccomp（policy 里 `enabled: false`）
3. 换权限（rootless → root）

## 数据对比

### 主表

先看默认环境（WSL 的 61 目录 PATH）：

| 档位 | runc（rootless） | runc（root） | zygote（root） |
| --- | --- | --- | --- |
| **最小** | 79.6 ms | **14.85 ms** | **3.82 ms** |
| **完整** | 74.8 ms | **15.0 ms** | **4.40 ms** |

把 PATH 换成 6 个目录再跑一遍 rootless：

| 档位 | runc（rootless，干净 PATH） | runc（root） |
| --- | --- | --- |
| **最小** | **18.6 ms** | 14.85 ms |
| **完整** | **20.2 ms** | 15.0 ms |

**两列一对比就看出：rootless 那 60ms 是 WSL 的 PATH 在收费，不是 user namespace。** 真正的 userns 成本只有 3.6~5.2ms。

### 比值

| 比法 | 数值 | 能不能讲 |
| --- | --- | --- |
| 同权限（root）、最小档 | 14.85 / 3.82 = **3.9×** | ✅ 机制效率 |
| 同权限（root）、完整档 | 15.0 / 4.40 = **3.4×** | ✅ 机制效率 |
| rootless（干净 PATH）vs zygote | 18.6 / 3.82 = **4.9×** | ⚠️ 混合了权限差异 |
| rootless（脏 PATH）vs zygote | 79.6 / 3.82 = **20.8×** | ❌ 其中 61ms 是 WSL 环境税 |

> ⚠️ **20.8× 绝对不能拿去讲**。那 61ms 是 WSL 的 PATH 搜索，换一个 Linux 发行版就不存在。
> **测量环境本身可能比被测对象贵一个数量级**——这是这一轮最大的教训。

## 三个反常点

### 反常点 1：削掉 38 次 mount，runc 一分钱没省

```
完整档  15.0 ms
最小档  14.85 ms     差 0.15ms
```

把 11 条掩蔽、6 条只读重挂、`/dev/pts` `/dev/shm` `/dev/mqueue` `/sys` 全部砍掉，runc 的时间纹丝不动。

**这直接推翻了一个此前写进草稿的推断**：当时按 03 篇的 strace 分段 × 统一比例缩放，算出“mount 占了三分之一左右”。实测不成立。原因见下文“strace 税”一节——**strace 对不同 syscall 的放大倍数根本不均匀**。

既然不是 mount，那 15ms 是什么？只能是 runc 的**架构固定成本**：

- 两次 Go 进程启动（`runc` 主进程 + re-exec 出来的 `runc init`）
- 完整 OCI 生命周期：`create` / `start` / `state` / `delete`
- state 文件读写、pipe 握手同步

这解释了为什么"优化配置"对 runc 的启动时间几乎无效——**瓶颈不在配置里**。

### 反常点 2：rootless 慢 65ms，但原因不是 user namespace

同一份最小配置、同样关掉 seccomp，只换权限：

```
rootless  79.6 ms
root      14.85 ms
```

第一反应是“user namespace 贵”。**先量一下这个猜测：单独建一个 userns 要多久？**

```
/bin/true                            978 µs   （基线：fork + exec）
unshare --user --map-root-user true 1738 µs
                                    ────────
                            净成本   760 µs
```

**0.76ms。不是 65ms——猜测被推翻。**

那就换个变量再试——只改 PATH，其他一动不动：

```
PATH 目录数 61（其中 31 个 /mnt/c/...）：79.6 ms
PATH 目录数  6（全在 Linux 文件系统）：18.6 ms
```

差 61ms，一拍即合。

**机制**：runc 在 rootless 下要 `LookPath("newuidmap")` / `("newgidmap")`——普通用户不能自己写 uid 映射，必须借这两个带特权的辅助程序代劳。而**本机这两个都没装**，所以每次都得把清单走完（“找不到”是最贵的查找）。

WSL 的 PATH 有 61 个目录，其中 31 个在 `/mnt/c`（drvfs），每次 `stat` 都要跨一层文件系统。实测在这个 PATH 下找一次不存在的命令要 **约 33ms**：

```
2 次 × 33ms ≈ 66ms   ← 与实测的 61ms 对上
```

**真正的 userns 成本**：

| 项 | 耗时 |
| --- | --- |
| 单独建 userns（`unshare --user`） | **0.76 ms** |
| runc rootless 相对 root 的全部增量（干净 PATH） | 3.75 ms（最小档）/ 5.2 ms（完整档） |

差的 3ms 是 rootless 路径里的**其他**动作（cgroup 权限探测等），不在 userns 本身。

这条同时解释了反常点 1 的一个侧面：为什么削 mount/seccomp 完全没效果——因为那 61ms 根本不在容器的配置里，在文件系统里。

### 反常点 3：只有 zygote 的时间随配置变化

```
最小  3.82 ms
完整  4.40 ms      +0.58ms（+15%）
```

runc 侧同样的改动是 +0.15ms，几乎看不见；zygote 侧却是 +0.58ms、占比 15%。

**不是 zygote 的 mount 更贵，而是它的基数太小。** 按 mount 次数折算，两边单价都在 25µs/次上下——只是 runc 那边被 15ms 的底噪淹没了，zygote 这边 3.8ms 的基数让 0.58ms 显了形。

这条对叙事有用：它证明**我们的 4ms 不是靠"少做加固"换来的**。把 17 项加固 + 4 项基础挂载全补上，代价只有 0.58ms。

---

## strace 税：5.9×

03 篇记录的 runc 段是 **441ms**（strace 下）。同一段裸跑是 **74.8ms**。

再从 trace.log 里数一下这段时间发了多少 syscall：

```
runc 段（execve runc → execve /probe）：9140 行 syscall
441ms − 74.8ms = 366ms ÷ 9140 ≈ 40µs/条
```

**每发一条 syscall，交 40µs 过路费。** 一万条就是 400ms。

这也解释了为什么"分段缩放"会错得离谱：动态链接器那一段（`mmap`/`openat` 密集）被放大得最狠，mount 段反而平缓。**统一比例缩放等于假设所有 syscall 一样贵，而这个假设不成立。**

> **教训：strace 的结构可信，绝对值和比例都不可信。** 以后引用 03 篇的数字必须带一句"strace 下 = 上界"。

## 结论与启示

### 1. 结论

1. **同权限下，zygote 比 runc 快 3.4~3.9 倍**：15.0ms vs 4.4ms（完整档）、14.85ms vs 3.82ms（最小档）；
2. **runc 的启动开销是架构固定成本，不随配置变化**：削掉 38 次 mount + 159 条 seccomp，只省 0.15ms；
3. **rootless 比 root 多 65ms，但那是 WSL 的 PATH 税**：压短 PATH 后只多 3.6~5.2ms，userns 本身很便宜；
4. **加固很便宜**：17 项掩蔽/只读 + 4 项基础挂载，总价 0.58ms；
5. **strace 放大约 5.9 倍**，摊到每条 syscall 约 40µs。

### 2. 教训

- **"快多少"必须先钉终点**：不钉在同一个瞬间，比出来的倍数是假的；
- **控制变量要先对齐功能**：runc 完整档 vs zygote 最小档，比的是"谁做的事多"，不是"谁更高效"；
- **实验会推翻推断，而且往往是好事**：这一轮推翻了“mount 占了三分之一”和“分段等比缩放”两个推断，两个都是纸面推演出来的；
- **基数决定可见性**：同样是 0.5ms 的改进，在 15ms 里是噪声，在 4ms 里是 15%——**看比例之前先看基数**；
- **测量环境本身可能比被测对象贵一个数量级**：61 个 PATH 目录（31 个在 `/mnt`）凭空造出 61ms，比整个 zygote 启动还长 15 倍；而单独建一个 userns 只要 **0.76ms**。
