# 01_沙箱的 ENOSYS“幻象”：seccomp 超界号码伪造行为的分析与实证定位

> 研究文档系列 01 ｜ 2026-09-22
> 项目：Anolix（轻量沙箱运行时核心，Go + runc）
> 本文所有数字与输出均来自本机真实运行（WSL2 Ubuntu / 内核 6.18 / runc 1.3.4 / libseccomp 2.5.5），无推断值。

---

## 背景

为了掌握容器运行时的**隔离与执法（enforcement）原理**——而不是停留在"会用 Docker"的层面——我决定从零实现一个轻量沙箱运行时：**Anolix**。

它不做隔离本体（那是内核与 runc 的职责），而是做三件事：**策略解析 → 翻译成 OCI 配置 → 管理容器生命周期**。定位是一套"可观测、可证伪"的沙箱外壳：

- **可观测**：每一次系统调用被拦截、被放行、返回值是什么，都能拿到一手证据；
- **可证伪**：任何一个"策略已生效"的结论，都必须是实验测出来的，而不是配置声明里写着的。

技术选型：Go 实现外壳（`config` 策略解析 / `launcher` OCI 生成与生命周期 / CLI），`runc 1.3.4` 作为 OCI 运行时，`runtime-spec v1.2.1` 对齐仓内规范；未引入任何其它外部依赖。

本文记录的是从**构建到一次完整问题定位**的全过程：沙箱跑起来之后，我在验证 seccomp 策略时遇到了一组反常的 errno 现象，最终定位其根因为 **libseccomp 生成过滤器时的内建伪造行为**，并由此总结出一套错误码观测方法。

## 一、地基构建：最小可运行的沙箱外壳

### 1.1 组件与启动链路

```
anolix run --policy examples/policy.json --rootfs ./rootfs -- /probe
   │
   ├─ config：   policy JSON（seccomp 开关 / errnoRet / 默认动作 / 放行名单）→ 严格校验
   ├─ launcher： 生成 OCI bundle（config.json）→ exec runc run → 透传退出码
   └─ 生命周期： 超时/中断先 SIGTERM 转发，兜底强杀 + runc delete 清理
```

沙箱基线（由 launcher 生成的 OCI spec 固化）：独立 pid/net/ipc/uts/mount/cgroup namespace；**能力集清空 + NoNewPrivileges**；seccomp 默认拒绝 + 白名单。非 root 用户下自动启用 **rootless**（user namespace + uid/gid 单映射 + devpts gid 适配），无需 sudo 即可运行。

### 1.2 rootfs 的极简化决策

容器内没有动态链接器，程序必须**静态编译**（`CGO_ENABLED=0`）——否则会报极具迷惑性的 `no such file or directory`（文件在，是找不到链接器）。因此 rootfs 被简化到极致：

```
rootfs/
├── probe    ← 全部内容就是一个静态 Go 探针（自检沙箱环境）
├── sysc     ← 系统调用探针（按号码"递申请单"）
└── tmp/     ← 1777 可写目录（容器 root 无 CAP_DAC_OVERRIDE，需要标准可写区）
```

没有 busybox、没有 libc——**"向沙箱注入程序"的本质就是往这个目录放文件**，没有第二条通道。

### 1.3 构建期的两次排障

**故障 A：runc 拒绝符号链接形式的 rootfs。**

最初实现是把 `bundle/rootfs` 做成符号链接指向真实 rootfs，运行直接失败：

```
ERRO runc run failed: invalid rootfs: not an absolute path, or a symlink
```

翻 runc 源码定位到 `libcontainer/configs/validate/validator.go`：该校验要求 `filepath.Clean(path) == EvalSymlinks(Abs(path))`，即**必须为规范化绝对路径、全链路无符号链接**。修复：不再建链，rootfs 经 `EvalSymlinks` 解析后把真实绝对路径直接写入 OCI `root.path`。

**故障 B：自定义 seccomp 白名单下容器 init 启动失败。**

裁剪白名单后，容器起不来，报错极具误导性：

```
ensure /proc/... is on procfs: function not implemented
container process is already dead
```

**原因分析**：runc init 与容器内 Go runtime 在过滤器装载后**自身仍会调用若干系统调用**（实测必需：`fstatfs`、`fcntl`、`eventfd2`、`unlinkat` 等）——白名单只覆盖业务代码所需调用时，这些 runtime 内部调用被拦截。当时策略的 `errnoRet=38 (ENOSYS)`，拦截被**伪装成"内核不支持"**，排查一度被引向"WSL2 内核缺特性"的方向。

> 这次故障已经引出了本文的核心主题：**被 seccomp 拦截的错误码，可以伪装成别的来源。**

## 二、基准实验：三世界 errno 对照

### 2.1 实验装置

写了一个"递申请单"探针 `sysc`：第一个参数是系统调用号码（进 `rax`），后面最多六个参数（进 `rdi/rsi/rdx/r10/r8/r9`）——即 x86-64 syscall ABI 的直接映射。

```
./sysc 41 2 1 0        # socket(AF_INET, SOCK_STREAM, 0)
```

同一份探针在**三个世界**各跑一遍：**宿主**（无过滤器，天然行为）／**沙箱+默认策略**（errnoRet=1）／**沙箱+example 策略**（errnoRet=1145）。

### 2.2 原始采样

| 号码（处境） | 宿主（无过滤器） | 默认策略（errnoRet=**1**，M=439） | example 策略（errnoRet=**1145**，M=435） |
| :--- | :--- | :--- | :--- |
| `41` socket（名单外） | **成功 fd=4** | **1** (EPERM) | **1145** |
| `170` sethostname（名单外） | **1**（天然 EPERM） | **1** | **1145** |
| `174` 表内空槽（名单外） | **38**（天然 ENOSYS） | **1** | **1145** |
| `436` close_range（默认名单内） | **0**（成功） | **0** | **38** |
| `439` faccessat2（默认名单内） | — | **14** (EFAULT，放行后天然) | — |
| `440` process_madvise | **9** (EBADF) | **38** | — |
| `9999`（表外） | **38** | **38** | **38** |

### 2.3 两个发现

**发现一：错误码会"撞脸"。** `170` 在宿主天然返回 1（无权限改主机名），与沙箱策略章的 1 **完全同码**——只看 errno 根本无法区分"被策略拦了"还是"天然没权限"。`174` 更危险：它在宿主天然就是 38，与"策略把它伪装成 38"同码。

**发现二：拦截返回的错误码由策略决定，可自由定义。** `41` 在两个策略下分别返回 1 和 1145——数字跟随 `errnoRet` 配置走，证明拦截无误、且"返回什么码"直接来自策略配置。

### 2.4 应对：哨兵 errno

既然 1、38 都有天然来源，我选定一个**自然界不可能出现**的数字作为"策略章"：

**`errnoRet = 1145`** —— 选取依据：真实 errno 上限为 **133**，seccomp 错误码数据域上限为 **4095**；取此区间内的值，任何一次观测到 1145，即可**单次确认**"这是 seccomp 拦截"，不再需要对照实验。（此前 example 曾用 38 作"伪装 ENOSYS"演示——这正是发现一"38 撞脸"的来源。）

## 三、异常发现：9999 的"恒定 38"

### 3.1 异常现象

对照表里最反常的一行是 `9999`：**它在两个策略下都返回 38**。按"拦截章随 errnoRet 变"的规律，它本应返回 1 / 1145——但它的返回值不受策略配置影响。

### 3.2 边界扫描

对两个策略分别做边界扫描，找到了行为切换点：

| 策略 | 放行名单最大号 M | M 点行为 | M+1 点行为 |
| :--- | :--- | :--- | :--- |
| 默认 | **439**（faccessat2） | 439 → 14（名单内，放行后天然） | **440 → 38** |
| example | **435**（clone3） | 435 → 22（放行后天然 EINVAL） | **436 → 38** |

**结论**：存在一个**动态边界 M = 放行名单最大号**；`nr > M` 的调用一律返回 38，**与 errnoRet 配置无关**。

### 3.3 反例：440

`440`（process_madvise）是关键证据：**宿主返回 9 (EBADF)——说明内核支持它、且执行到了**（fd 非法才报 EBADF）。但默认沙箱（M=439）里它返回 **38**。

> 如果沙箱里的 38 是"内核不支持"的真实结果，那么内核明明支持的 440 不可能得到它。**据此可判定：超界 38 是一种伪造。**

## 四、根因定位：手写 BPF 对照实验

### 4.1 实验设计

此时存在两个待排除的假设：

- **假设 A**：内核不把"表外号码"（如 9999）交给 seccomp 过滤器，38 是内核直接退的；
- **假设 B**：过滤器看得见一切号码，超界 38 是**生成过滤器的库**（runc 所用的 libseccomp）内建写入的。

为引入一个**行为完全已知的白盒对照组**，我用 raw `sock_filter` 指令手写了一枚极简 seccomp BPF 过滤器（不经过 libseccomp）：只放行 12 个程序自身运行必需的系统调用（write/exit/futex 等，供程序自己打印与退出），其余一切号码——**无论是否超出内核系统调用表**——一律返回特征值 `ERRNO(1234)`。

### 4.2 原始输出

```
手写 seccomp 过滤器已安装（非 libseccomp）；盖章值 = 1234
  nr=39    → 被盖章: errno=1234（过滤器看得见这个号码）
  nr=170   → 被盖章: errno=1234（过滤器看得见这个号码）
  nr=174   → 被盖章: errno=1234（过滤器看得见这个号码）
  nr=9999  → 被盖章: errno=1234（过滤器看得见这个号码）
```

**9999 被成功盖章**——在过滤器写者决定盖章值（1234）的前提下。这一结果：

1. **推翻了假设 A**：内核会把任何号码（含表外）交给过滤器——"表外号码过滤器看不见"不成立；
2. **假设 B 成立**：既然判决完全由过滤器内容决定（1234/38 随写者），而沙箱里超界号码的 38 又随 M 边界精确切换——**"超界→ENOSYS"只能是 libseccomp 编译过滤器时的内建行为**。

### 4.3 结论：三层责任链

```
【内核】seccomp 机制    = 钩子 + 忠实执行 BPF 判决（不认识号码对错）
【库】  libseccomp      = 把规则集编译成 BPF（黑盒出处：超界伪 ENOSYS 写在这里）
【项目】policy.json     = 规则内容（errnoRet / 名单），经 runc 递交给 libseccomp
```

### 4.4 为什么库要伪造

考察 libseccomp 的处境：编译时它知道"规则集只覆盖到 M"，对 M 以上的号码**没有用户规则可依据**。此时套用用户的 default action 会更糟（配 EPERM 会打断程序对新调用的"降级探测"——glibc 的 clone3 曾因此被坑；配 KILL 会直接杀程序）。返回 **ENOSYS（"装作此调用不存在"）是对未知号码唯一安全的答复**——与 runc 社区"未知 syscall 应返回 ENOSYS"（issue #2151）的方向一致。

## 五、结论

### 5.1 三档决策模型（最终版）

```
                       调用号码 nr
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
    nr ∈ 名单?           nr ≤ M ?              nr > M ?
        │是                 │是（不在名单）       │是
        ▼                   ▼                   ▼
     【放行】           【策略章】            【伪造章】
    内核真执行          errnoRet=1145        ENOSYS(38)（libseccomp 内建）
    （天然结果）        【项目可配】          【改 errnoRet 无效】
```

沙箱内 errno 的三种来源：**放行 = 天然结果；≤M 拦截 = 策略章；>M = 伪造章**。同一个 38 在宿主上来自内核"查无此号"，在沙箱里来自 libseccomp 的伪造——数字相同，来源不同。

### 5.2 方法论沉淀

1. **差分对照**：单列观测无意义（1/38 会撞脸）——宿主 vs 沙箱、跨策略对照、边界扫描（M/M+1）三件套；
2. **哨兵化**：选取"只有本策略能产生的数字"（133 < x < 4095），实现单次观测即可确认；
3. **白盒对照组**：为排除嫌疑，构造行为完全已知的替代品（手写 BPF）——**实验的价值在于它能推翻你自己的假设**；
4. **来源标注**：每个结论标明【内核固定】/【库行为】/【项目自定义】，责任边界清晰。

### 5.3 工具链产物

| 工具 | 作用 |
| :--- | :--- |
| `sysc` | 按号码递单的 syscall 探针（含 raw 模式，观察 rax 原始写回值） |

| `rawfilter` | 手写 BPF 白盒对照组（本篇定位根因的关键装置） |

### 5.4 教训

- **拦截错误码的可观测性，必须在策略设计时就考虑**：EPERM/ENOSYS 这类"常见码"会与天然错误撞脸，把调试引向错误方向；
- **"结果相同"不等于"来源相同"**：9999 的 38 在两处同值却因果链完全不同，判据是"判决发生在过滤器层还是内核表层"；
- **超界号码是策略边界（M）的函数**：删改放行名单会连锁改变其他号码的返回值——这是名单最大值的隐性耦合，实测在案。
