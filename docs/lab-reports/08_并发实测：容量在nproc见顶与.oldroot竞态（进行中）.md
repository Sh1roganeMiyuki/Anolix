## 背景

07 把单次启动钉在了同一个终点：同权限完整档 15.0 / 4.40 = 3.4×。
但 zygote 的卖点不是“第一个快”，是“第 100 个还一样快”。

单次数据回答不了这个问题：

- 吞吐 = K / 窗口，不是单次延迟的倒数；
- 并发下每个请求的起点不同，没有共同时间轴就无法对账；
- 测量工具自己也会抢 CPU。

08 要回答三件事：

1. K 个同时 spawn，延迟、吞吐、CPU 怎么变？
2. 瓶颈是 CPU 吗？
3. 并发会不会暴露单次测不出的 bug？

## 结论速览

**1. 延迟随 K 线性涨，吞吐在 nproc 处腰斩**

```
p50:   K=16 9.3ms  →  K=64 34.0ms    （K 涨 3.56×，延迟涨 3.66×）
吞吐:  K=16 1930/s →  K=64 984/s
```

线性 = 排队（每个请求处理量不变，只是要等），不是撞上容量墙。

**2. 不是 CPU**

| 账 | 来源 | K=64 |
|---|---|---|
| worker 的 CPU | `ANOLIX_REAP` 的 `cpu_ns` 合计 ÷ 窗口 | 6.1 核 |
| 母体的 CPU | 母体全部线程 `/proc/<pid>/task/*/schedstat` 运行 ÷ 窗口 | 1.3–2.4 核 |
| 合计 | | **7.6–8.5 核 / 16** |

两本账不能混：6.1 是 worker-init + payload 烧的，1.5 是母体（accept / clone / cgroup）烧的。

时间是花在真活上：

```
payload（worker 装修）  13.1ms  50%
clone（fork + execve）   9.7ms  37%
cgroup                   2.0ms   8%
其余                     1.2ms   5%
```

**3. 并发暴露了一个真 bug**

`.oldroot` 竞态：K=64 首轮 **6/64** 失败（pivot_root ENOENT），修复后 **64/64**。
这是全文唯一闭环的一条（现象 → 根因 → 修复 → 复跑）。

**4. 测量本身翻了一次车**

`schedtrace` 的观测者效应把 read 的 p90 从 1ms 抬到 27ms，我据此写过错误结论。
细节见“一次翻车记录”。

## 实验设计

### 口径（三个旋钮）

- **起点**：每个客户端发请求前的 `CLOCK_MONOTONIC`（`SPAWN_META.dispatch_ns`）。
- **终点**：payload 第一条用户态指令（`PAYLOAD_META.abs_ns`，tprobe 一进 `main` 就取）。
- **窗口**：最早 dispatch → 最晚 abs。吞吐 = K / 窗口。
- **条件**：nproc=16；母体 `--warm 64 --cgroup --cg-memory 256 --cg-pids 200`；K=1/16/64；单轮。

### 九点打点，按 id 归并

| 行 | 产出方 | 字段 |
|---|---|---|
| `SPAWN_META` | spawn 客户端 | `dispatch_ns` / `after_dial_ns` / `write_ns` / `after_write_ns` / `response_ns` |
| `ANOLIX_MOTHER` | 母体 | `accept_return_ns` / `handle_start_ns` / `accept_ns` / `cgroup_ns` / `clone_done_ns` |
| `PAYLOAD_META` | tprobe | `abs_ns` + run id |
| `ANOLIX_REAP` | 母体收尸 | worker 的 utime+stime |

九个点都在同一根 `CLOCK_MONOTONIC` 上（raw syscall，不是 wall clock，不受 NTP 调整），
相邻两点相减就是一个段。并发下日志顺序不可信，所以按 id 归并，不按行号。

> v1 只有三个点（dispatch / accept / clone_done），只能拆四段。
v2 加入 `accept_return_ns`、`handle_start_ns`、`after_dial_ns`、`after_write_ns` 后能拆九段。

### 为什么客户端不用 sudo

特权动作都在母体（clone、cgroup、mount），socket 是 0666。客户端提权只会引入
`sudo secure_path` 这个额外变量（07 的 PATH 税）。

### 为什么要 `ANOLIX_MOTHER`

没有它，只能看到“客户端回包”；而母体是在 `cmd.Start()` 成功后就回包，payload 还没跑。
K=16 时回包 p50 5.9ms，payload p50 16.1ms——两个终点差约 10ms。

### 工具与原始数据

`scripts/zygote/conc.sh`；原始数据落 `.bench-tmp/conc/<tag>/`（不入库）。
K=1/16/64 的 tag 见附录。

## 数据

### 主表 A：R 轮（热态，连续 5 轮，W=0）

同一母体、同一台机器，连续 5 轮，轮间隔 1s。下表为中位数（括号内是 5 轮的最小–最大）。

| K | p50(ms) | p95(ms) | 起跑斜坡(ms) | 完成跨度(ms) | 吞吐(spawn/s) | CPU(核/16) |
|---|---|---|---|---|---|---|
| 16 | 9.5 (8.7–9.8) | 13.2 (12.0–15.0) | 5.1 (4.0–5.4) | 8.3 (7.6–12.0) | **1930** (1329–2094) | 5.1 |
| 64 | 27.7 (18.7–35.7) | 55.3 (43.5–74.6) | 28.6 (24.4–51.7) | 65.0 (53.7–82.2) | **984** (778–1193) | 6.1 |

口径：

- 吞吐 = K ÷ **完成跨度**；完成跨度 = 最后一个 payload 的 `abs` − 第一个 payload 的 `abs`，**不含斜坡**。
- K=16 取 4 轮：第 5 轮斜坡 10.2ms（其余四轮 4.0–5.4ms）、p50 19.8ms，判为环境抖动，剔除。
- CPU = `ANOLIX_REAP` 的 `cpu_ns` 合计 ÷ 窗口（窗口仍是“最早 dispatch → 最晚 abs”）。

### 两个口径问题（都踩过）

**1. `K ÷ 窗口` 会把斜坡算进分母**

同一个 K=16，五轮里这个数从 244/s 到 868/s—— 3.6 倍差，全在斜坡（占窗口 39–42%）。
所以吞吐改用 `K ÷ 完成跨度`（第一个完成 → 最后一个完成）。

> 早期版本写过“吞吐 632 → 509”，那是 `K÷窗口` 的产物，已作废。

**2. 前几轮是冷轮**

同一台机器、连续 5 轮，斜坡单调下降（K=16：43.6 → 5.2ms；K=64：127 → 27ms）。
**第 1 轮比第 5 轮慢 5–7 倍**，所以“R 轮取中位数”是错的，前几轮必须剔除。

⚠️ 冷轮成因未定位（候选：page cache、CPU 频率、调度器状态）。只按“斜坡是否收敛”判定冷热。

### 九段拆分（K=64，干净口径，3 轮 n=192）

用 p50（典型请求），不用平均值——平均值会被少数极端值拉高（见下节翻车记录）。

| # | 段 | p50(ms) | p90(ms) | p95(ms) |
|---|---|---|---|---|
| 1 | Dial | 0.07 | 0.17 | 0.39 |
| 2 | 准备请求 | 0.002 | 0.003 | 0.004 |
| 3 | write 执行 | 0.12 | 0.22 | 0.29 |
| 4 | write 完成 → 母体 accept 返回 | 0.70 | 5.23 | 5.64 |
| 5 | → goroutine 开始 | 0.20 | 9.47 | 12.69 |
| 6 | → read 完成 | **0.05** | 1.06 | 2.07 |
| 7 | → cgroup 建完 | 2.04 | 13.15 | 16.19 |
| 8 | → clone 完成 | **9.73** | 18.38 | 20.86 |
| 9 | → payload 第一行 | **13.14** | 24.32 | 29.85 |

典型请求（p50）的钱花在哪：

| 段 | p50 | 占比 |
|---|---|---|
| payload（worker 装修 + 起 tprobe） | 13.1ms | 50% |
| clone（母体 fork + execve worker-init） | 9.7ms | 37% |
| cgroup | 2.0ms | 8% |
| 其余（连接 / 读 / 调度） | 1.2ms | 5% |

三个结论：

1. **客户端无罪**：Dial + 准备 + write 合计 0.19ms。
2. **read 无罪**：0.05ms，占 0.2%。
3. **payload + clone = 87%**，而且这两段都是“真活”（fork/exec + mount/seccomp），不是空等。

### K 缩放：延迟随 K 线性增长，不是断崖

| K | p50(ms) | read p50(ms) | 窗口(ms) |
|---|---|---|---|
| 16 | 9.3 | 0.18 | 13–25 |
| 18 | 9.3 | 0.12 | 17 |
| 20 | 10.2 | 0.15 | 17–19 |
| 25 | 11.9 | 0.13 | 21–23 |
| 32 | 15.5 | 0.08 | 30–46 |
| 64 | 34.0 | 0.15 | 64–75 |

```
K:    18  →  64    （3.56×）
p50:  9.3 → 34.0   （3.66×）
```

**延迟与 K 成正比**：这是排队（每个请求的处理量不变，只是要等），不是容量断崖。
read 全档平坦（0.08–0.18ms），**不存在“K=64 断崖”**。

图形（条形长度 = p50；X 轴是档位序号，**非等距**）：

```text
              p50(ms)                                  吞吐
K=16      ████████▌ 9.3                          1930/s   ← nproc
K=18      ████████▌ 9.3
K=20      █████████ 10.2
K=25      ██████████▊ 11.9
K=32      █████████████▊ 15.5
K=64      █████████████████████████████████ 34.0     984/s
```

形状：16–25 几乎平的，32 开始抬头，64 陡上去。**拐点在 nproc 后面，不在 nproc 上面。**

单段涨幅对照（K=1 → K=64）：

| 段 | K=1 | K=64 | 涨幅 |
|---|---|---|---|
| clone | 0.88ms | 9.73ms | **11×** |
| cgroup | 0.26ms | 2.04ms | 7.8× |
| payload | 5.6ms | 13.14ms | 2.3× |

clone 涨得最凶，是下一步该查的：fork 之后母体要**同步等**子进程 execve 一个 3MB 的 Go 程序。

### 一次翻车记录：schedtrace 的观测者效应

有一批数据是母体带 `GODEBUG=schedtrace=10` 跑的（每 10ms 打印一次调度器状态）。同一个 K=64：

| | read p50 | read p90 |
|---|---|---|
| 带 schedtrace | 0.40ms | **27ms** |
| 不带 | 0.05ms | 1.06ms |

差 27 倍。当时据此写过“read 在 K=64 断崖、占 24.6%”，**是错的**：

- 错误一：用了平均值，被那 27ms 的长尾拉到 9ms；
- 错误二：没意识到 `schedtrace` 每 10ms 抢一次 runtime 全局锁 + 写一次文件，本身就是干扰源。

教训：**观测工具要先进账。** 任何“打印”型工具（schedtrace、gctrace、频繁 log）
都会改变被测对象；能只用只读计数器（`/proc/<pid>/...`）就别开打印。

### 已排除的假设

| 假设 | 验证方法 | 结果 | 数据条件 |
|---|---|---|---|
| 客户端写请求慢 | after_dial / write / after_write 三点 | 0.19ms → **排除** | 干净 |
| read 是瓶颈 | 九段拆分 | p50 0.05ms → **排除** | 干净 |
| log 包全局 mutex | `--quiet` 把 5 条/请求降到 1 条 | p50 33.0→29.0（噪声内）→ **排除** | 干净 |
| 绑核隔离能改善 | 母体绑 8–15、客户端绑 0–7 | queue 只降 22%，p50 27.7→41.0 → **净亏** | 干净 |
| CPU 竞争 | `schedstat` 的运行/等待增量；schedtrace 的 runqueue/idle | 母体只占 1.3–2.4 核 / 16 → **不是算力** | 部分带 schedtrace |
| GC STW 是主因 | `GOGC=400` 让窗口内 GC 归零 | p50 33.6 vs 33.0 → **不变** | ⚠️ 带 schedtrace，待复验 |

> 最后一行要标清楚：那次 GC 对照是在带 schedtrace 的母体上做的，
> “GC 不影响”这个结论需要在不带 schedtrace 的条件下再跑一次才算数。
>
> `--quiet`、`schedtrace`、`GOGC` 都是归因时临时加的旋钮，默认关闭，不进正式口径。

## 现象：并发第一枪打中 .oldroot

K=64 首轮 **6/64** 失败，日志是：

```
worker-init: rootfs 设置失败: pivot_root 失败: no such file or directory
```

- **根因**：rootfs 是所有 worker 共享的同一个宿主目录；`.oldroot` 是里面的普通目录。
  A 换根后 `rmdir` 删的是共享目录项，B 在 `mkdir` 与 `pivot_root` 之间就找不到 put_old。
- **两种交错**：
  1. B 先 `pivot_root` → 目录成为挂载点 → A 的 `rmdir` 吃 `EBUSY` → B 成功。
  2. B `mkdir` → A `rmdir` → B `pivot_root` 找不到 put_old → `ENOENT` → 6/64。
- **修复 A（采用）**：只 `umount`，不 `rmdir`；`.oldroot` 常驻空目录。
  - 代价：payload 的 `/` 下多一个空目录；rootfs 必须可写或预建。
  - 放弃唯一目录名（崩溃留垃圾、需清理）；放弃每 worker 独立 rootfs（复制成本、违背共享初衷）。
  - 失效条件：rootfs 只读时 A 不成立，需预建 `.oldroot` 或改用唯一名。
- **验证**：修复前 6/64 ENOENT；修复后 3 次 K=64（含一次冷启动）**均 64/64**。
  仍属必要非充分证据。

> 这是 08 目前唯一的闭环：现象 → 根因 → 修复 → 复跑。
