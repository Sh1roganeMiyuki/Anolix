# 10_一次归因翻车：3.4× 不是"少一次 clone"

> 环境：WSL2 / 内核 6.18 / 16 vCPU（8 物理核）/ runc 1.3.4 / crun 1.14.1
> 数据来源：09 的三路径主表（root，N=30，p50，完整档）+ 08 的 zygote 单发分段
>
> **一句话**：3.4× 曾被归因为"少一次进程创建"。逐层量化后：clone 只值 0.5 ms，
> 加载 runtime 只值 0.45 ms；而 runc 与 crun 那 7.15 ms 差距里，**有 6.7 ms 是 runc 在复制自己 11.4 MB 的二进制**
> （exeseal：防容器进程改写宿主 runc 二进制，CVE-2019-5736 那一类）——是安全加固，不是启动必需的一步。

---

## 背景

07 把 3.4× 归到"runc 的架构固定成本"；09 补了 crun 作为第二对照（1.6×）。
两份文档都停在"结构差异"这一层，没有拆到具体是哪一块。

笔记里我把它进一步简化成一句话：

> zygote 快，是因为它只 clone 一次，runc 要两跳。

这句话好记，也一直在口头复述里用。**它是错的。**

---

## 起因：为了画一张图，去抓了一次 strace

要给三条路径画对比图。凭记忆画的话，runc 那段只能写出"主进程 + init"，
谁 fork 谁、execve 几次、pid 怎么变，全靠印象。

于是抓真实序列，只过滤进程创建与程序替换：

```bash
strace -f -qq -e trace=clone,clone3,execve \
  -o /tmp/runc-trace.txt ./anolix run --runtime /usr/sbin/runc \
  --rootfs ./rootfs -- /tprobe
# crun 同样命令，只换 --runtime
```

---

## 数据一：runc 的序列（rootless）

```text
execve("/usr/sbin/runc", ["--root","/tmp/rt-s","run","--bundle",...])
  clone(CLONE_VFORK) = 336684
  execve("/proc/self/fd/6", ["/usr/sbin/runc","init"])     ← re-exec：Go runtime 第 2 次加载
    clone(CLONE_PARENT|SIGCHLD) = 336686
    clone(CLONE_PARENT|SIGCHLD) = 336687
      execve("/tprobe")                                    ← payload
```

两个此前没写进文档的事实：

1. **re-exec 真实发生**：`execve("/proc/self/fd/6", ["runc","init"])`。
2. **double fork 也是真的**：两次 `clone(CLONE_PARENT)`，让容器进程被上层收养，
   而不是挂在 `runc init` 名下。

---

## 数据二：crun 的序列（rootless）

```text
execve(".tools/crun-root/usr/bin/crun", ...)
  clone(CLONE_NEWUSER)                                     ← userns 载体
  clone → execve(newgidmap) ×6（全 ENOENT）                 ← 写 gid_map 的辅助程序
  clone → execve(newuidmap) ×6（全 ENOENT）                 ← 写 uid_map 的辅助程序
  clone → execve(payload)                                  ← 容器进程；setup 在同一份 C 代码里做完
```

数一下进程级 clone：

```text
runc 内部：3 次（re-exec + double fork ×2）
crun 内部：4 次（userns 载体 + 两个 map 辅助 + 容器进程）
```

**crun 的进程更多，却快 2.1×。** 这一条直接打死了"进程数是原因"。

---

## 数据三：zygote 自己的账

09 的 zygote 只测了总时长（4.05 ms），没有分段。分段数据来自 08 的 K=1（7.0 ms），
但那一组是**单样本**，且绝对值比 09 高 3 ms（单样本 + 热身不足；09 是 30 个样本取 p50）。
**所以只用它的比例，不用它的绝对值。**

| 段 | 08 K=1 (ms) | 占该次的比例 |
| --- | ---: | ---: |
| socket + 排队 | 0.30 | 4.3% |
| cgroup | 0.26 | 3.7% |
| **clone** | **0.88** | **12.6%** |
| worker 侧（挂载 + pivot + seccomp + execve + Go runtime） | 5.59 | 79.4% |

按这个比例推算 09 的 4.05 ms：**clone ≈ 0.5 ms**（量级估计，非直接测量）。

而 runc 与 zygote 的差距是 `13.66 − 4.05 = 9.61 ms`：

```text
clone 能解释的上限：~0.5 ms（推算）
实际差距：            9.61 ms
差约 19 倍
```

⚠️ 这个换算的强度有限：比例来自另一批样本、另一个单次。
即使把比例误差算到 2 倍（clone 占 25%），也只有 1 ms，仍然解释不了 9.61 ms。
**结论对比例不敏感，但对“clone 不是大头”这个判断是稳健的。**

---

## 推论：被推翻的是什么

不是"zygote 只 clone 一次"这个事实（它是对的），
而是**把它当成 3.4× 的原因**。

```text
固定成本 = 加载 runtime + 走 OCI 生命周期 + setup

runc   ：2 次 runtime 加载  + 走 + setup
crun   ：1 次 runtime 加载  + 走 + setup
zygote ：0 次 runtime 加载  + 不走 + setup（clone 只是 setup 的第一步）
```

三段差值：

| 区间 | 差值 | 至少包含 |
| --- | ---: | --- |
| runc → crun | 7.15 ms | 少一次 Go runtime 加载；另含 11 MB 与 0.4 MB 二进制的 page-in 差异、更重的 OCI 实现 |
| crun → zygote | 2.46 ms | 不解析 config.json、不写 state、不走 create/start、不加载 runtime |
| 合计 | 9.61 ms | = 3.4× |

clone 不在任何一格里占主要位置。

---

## 量化：三段能对上的账

“加载 runtime + OCI 生命周期”仍然是个复合词。这一节把它拆到可以相加的程度。

### 方法：三个可直接测的量

| 测什么 | 怎么测 | 扣什么 |
| --- | --- | --- |
| runtime 加载 | `runc --version` / `crun --version` | 减 `/bin/true`（C 裸底 0.73ms） |
| anolix 自身 | 07 的分段：准备 bundle | 0.6ms |
| payload 侧语言运行时 | 同一切口下换 payload：`/tprobe`（Go 2.3MB）vs `/cprobe`（C 767KB） | 两者相减 |

数据（rootless，N=30）：

```text
/bin/true（C 裸底）          0.73 ms
anolix -h（Go 加载+flag）    1.63 ms   → Go 加载 ≈ 0.90 ms
crun --version             2.38 ms   → crun 加载 ≈ 1.65 ms
runc --version             2.84 ms   → runc 加载 ≈ 2.11 ms

anolix+crun /tprobe（Go）   11.5 ms
anolix+crun /cprobe（C）    10.2 ms   → payload 的 Go 启动 ≈ 1.3 ms

runc list                  2.97 ms
runc --version             2.81 ms   → “读状态目录”≈ 0
```

### 分解（root 口径的 13.66 / 6.51 / 4.05）

```text
runc   13.66 = anolix 0.6 + runc 加载 2.1 + exeseal 复制 ~6.7 + OCI与setup ~3.0 + payload Go 1.3
crun    6.51 = anolix 0.6 + crun 加载 1.65 +                    OCI与setup ~3.0 + payload Go 1.3
zygote  4.05 =                 worker-init 加载 1.3 +          setup       ~1.5 + payload Go 1.3
```

⚠️ 这几栏都只保留两位有效数字。“OCI与setup”是减法算出来的，不是独立测量，
精确到 0.01 是假精度。

校验：

```text
runc − crun   = (2.1 − 1.65) + 6.7 = 0.45 + 6.7 = 7.15   ✓（实测 7.15）
crun − zygote = 0.6 + 1.65 + 3.0 − 1.3 − 1.5 = 2.45      ✓（实测 2.46）
```

### 这张表推翻了什么

1. **“加载 runtime”只值 0.45ms**（runc vs crun 的加载差），不是 7.15ms 的原因。
   原因在那一栏 **~6.7ms**，而它里面最大的一块是 exeseal 复制（见下节）。
2. **zygote 也不是“零成本”**：它有 1.3ms 的 worker-init Go 加载 + 1.3ms 的 payload Go 加载。
   它真正省下的是 **OCI 与 setup 那一整栏**（约 3.0 → 约 1.5）。
3. **"runc 慢"的账里，最大一栏是 `exeseal` 在复制 11.4 MB 的二进制**——
   一件和容器启动完全无关的加固。它比"运行时选型（Go vs C）"重要约 15 倍。

### 找到了那 ~9.7 ms 的大头：runc 在复制自己的 11.4 MB

`runc --debug` 日志的第一行：

```text
F_GET_SEALS on /proc/self/exe failed: invalid argument
could not use overlayfs for /proc/self/exe sealing -- falling back to making a temporary copy
cloning /proc/self/exe binary (11431736 bytes)
runc exeseal: using /proc/self/exe clone
```

runc 1.3 每次 `run` 都会把 `/proc/self/exe`（它自己，11.4MB）复制一份，
然后 **execve 那份副本**。这个机制叫 exeseal。

**它在防什么**

容器里的 1 号进程（也就是 payload）能够通过 `/proc/<父进程>/exe` 摸到宿主机上的
runc 二进制文件。如果它以写方式打开那个文件：

```text
宿主机上的 /usr/sbin/runc 被改写
  → 下一次任何人在宿主机上跑 runc，跑的就是被污染的版本
  → 容器逃逸，宿主机沦陷
```

这就是 CVE-2019-5736。影响面是所有“用 OCI 运行时拉起容器”的实现。

**复制为什么能防**

复制之后，容器进程看到的 `/proc/self/exe` 变成：

```text
副本（一次性的，进程退出就没了）
而不是 /usr/sbin/runc
```

payload 就算写，也只写到副本，宿主机上的二进制毫发无损。

**代价**

每次 `run` 复制 11.4MB。在这台机器上约 6.7ms —— 正好是 runc 与 crun 差距的主体。

⚠️ “execve 那份副本”这一步是推的：strace 里能看到 runc 主进程有第二次 execve，
但参数不可解码（地址空间已换），本机没再验证。

三处独立证据：

**1. 日志直接报出字节数**：11431736，与 `stat` 得到的 runc 二进制大小完全一致。

**2. `sendfile` 只在 `run` 出现**：

```text
runc --version   sendfile 0 次
runc list        sendfile 0 次
runc run         sendfile 1 次（strace 下 12855 µs）
```

这同时解释了“`list` ≈ `--version`”：两者都不做复制。

**3. 数量级吻合**：11.4 MB ÷ 1.7 GB/s ≈ 6.7 ms，与差值一致。

crun 的 `--debug` 日志里 copy / seal 相关 0 次——它不做这件事。

所以分解表里那一整栏（~9.7 ms）拆成：

```text
runc 的 OCI与setup  = exeseal 复制 ~6.7 + 其余的 ~3.0
crun 的 OCI与setup  =                        ~3.0
```

**两侧剩下那一段落在同一量级**——去掉 exeseal 之后，runc 与 crun 的容器创建成本
差不出一个可辨认的量。

⚠️ 不要说“两边完全相等”。两个 3.0 是减法算出来的，不是两次独立测量；
挖掉 exeseal（6.7 本身也是推算值）之后再相减，剩下的差值落在这场测量的分辨率以内。
**可以说的是“量级相同”，不能说“数值相同”。**

⚠️ **环境前提**：日志里那句
`could not use overlayfs for /proc/self/exe sealing -- falling back to a temporary copy`。
在能用 overlayfs sealing 的文件系统上，这段成本可能不存在或低很多。
所以这条结论绑定“runc 1.3.4 + 本机文件系统”，不是 runc 的普遍属性。

### 补充：那 352 次 futex 是什么

`strace -c` 的 syscall 画像（rootless 各一次）：

| syscall | runc | crun |
| --- | ---: | ---: |
| `futex` | **352** | **0** |
| `nanosleep` | **199** | **0** |
| `epoll_pwait` | 9 | **0** |
| `read` | 35 | 25 |
| `mmap` | 75 | 96 |

⚠️ 耗时列不可信（每条调用停两次），但**调用次数**可信。

这三类在 crun 里全为零，指向的不是“多加载一次”，而是**进程里一直有一个活着的 Go runtime**：

```
futex       → goroutine 调度 + GC 同步
nanosleep   → runtime 定时器（sysmon）
epoll_pwait → netpoll
```

它的绝对耗时没有测出来（把 futex 从一次 run 里剔出去做不到），
但可以确定它是那 ~3.0 ms 里的一部分，而不是 6.7 ms 的主体。

### 这张表的强度（必须带上）

- **实测项**：`/bin/true`、`anolix -h`、`runc/crun --version`、`runc/crun list`、payload 的 Go vs C。
- **差值推算项**：三个“OCI 与 setup”都是总时长减掉实测项算出来的，没有直接测量。
- **口径差**：实测都是 rootless，分解表用的是 root 口径的 13.66 / 6.51 / 4.05；
  两边结构相同，但绝对值不可直接相加，只有比例有意义。
- **payload 的 1.3ms 来自 crun 口径**（runc 那组噪声过大：20.8–28.5ms）。

要把它变成真测量，需要 runc/crun 内部的阶段日志——两家都不是为测量设计的，
`runc create` 在本环境又跑不了（`/proc/<pid>/setgroups` 只读）。

## 边界：哪些是数出来的，哪些是推出来的

必须写清区别，否则就是用一个新的未验证解释，换掉一个旧的未验证解释。

**数出来的（直接测量）**

- 进程数不是原因：crun 4 个进程 > runc 3 个，却快 2.1×。
- runc 内部确实 re-exec + double fork。
- clone 只占 zygote 自身 12.6%。
- Go runtime 加载 ≈ 0.90 ms；runc 加载 ≈ 2.11 ms；crun 加载 ≈ 1.65 ms。
- payload 的 Go 启动 ≈ 1.3 ms（Go payload vs C payload）。
- “读状态目录”几乎免费（`runc list` ≈ `runc --version`）。

**推出来的（差值，不是直接测量）**

- 三个“OCI 与 setup”栏位（~9.7 / ~3.0 / ~1.5），全部是减法推算，且只保留两位有效数字。
- zygote 的 worker-init 加载 1.3 ms（按 anolix 的 Go 加载类推）。
- 分解表用的是 root 口径总时长，但实测项都是 rootless；
  两边结构相同，**只有比例有意义，绝对值不可相加**。

**仍未知**

- 剩下的 ~3.0 ms 里，“OCI 协议工作”与“Go runtime 运行期活动”各占多少。
  futex / nanosleep / epoll 的存在说明后者不为零，但量没测出来。

## 可复用判据

> **如果真是 X 导致的，去掉 X 应该能省多少？**
> 拿这个数去比实际差值——对不上，X 就不是主因。

这次：

```text
X = clone         → 上限 0.5 ms
实际差值          → 9.61 ms
对不上 19 倍      → clone 不是主因
```

同一个判据也可以用在反方向。要证明"cgroup 是主因"：
先算 cgroup 段的量级（6.7 ms），再比"关掉 cgroup 后总时间的变化"
（27.4 → 26.0，只差 1.4 ms）——对不上，说明 cgroup 的时间会被别的等待吸收，
不是净成本。

## 教训

1. **分段数据只能说明"这一段占多少"，不能说明"它是原因"。**
   一个占 12.6% 的段，再怎么优化，天花板也只有 12.6%。
2. **一个解释如果没被反面验证过，它就还是假设。**
   这次的反面验证很便宜：数一下对方的进程数。
3. **结构图不要凭记忆画。**
   记忆保存的是简化版（"runc 主进程 + init"），而简化版会把"为什么"一起简化掉。
4. **一个解释可以被量化三次，每次都变小一格。**
   第一次：clone 是原因（12.6% → 推翻）。
   第二次：加载次数是原因（0.45 ms → 推翻）。
   第三次：OCI 与 setup 是最大一栏——再拆下去，里面最大的是 exeseal 复制（6.7 ms）。
   每量化一层，原来的"主因"就缩一格——这是好事，不是失败。
5. **最大的一笔可能和你的业务逻辑完全无关。**
   那 6.7 ms 里没有一行在"启动容器"，全在复制自己的二进制。
   只盯着代码看，永远猜不到这一笔。
