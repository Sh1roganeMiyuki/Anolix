# 10_一次归因翻车：3.4× 不是"少一次 clone"

> 环境：WSL2 / 内核 6.18 / 16 vCPU（8 物理核）/ runc 1.3.4 / crun 1.14.1
> 数据来源：09 的三路径主表（root，N=30，p50，完整档）+ 08 的 zygote 单发分段
>
> **一句话**：3.4× 曾被归因为"少一次进程创建"。一次为了画图的 strace 推翻了它——
> 进程数不是原因（crun 的进程更多却更快），clone 只占 zygote 自身 12%（约 0.5 / 4.05 ms），
> 解释不了 9.61 ms 的差距。真正被消掉的是"加载 runtime"与"走 OCI 生命周期"。

---

## 背景

07 把 3.4× 归到"runc 的架构固定成本"；09 补了 crun 作为第二对照（1.6×）。
两份文档都停在"结构差异"这一层，没有拆到具体是哪一块。

笔记里我把它进一步简化成一句话：

> zygote 快，是因为它只 clone 一次，runc 要两跳。

这句话好记，也一直在口头复述里用。**它是错的。**

---

## 起因：为了画一张图，去抓了一次 strace

要给三条路径画对比图。凭记忆画的话，runc 那段只能写出"主进程 + init"，
谁 fork 谁、execve 几次、pid 怎么变，全靠印象。

于是抓真实序列，只过滤进程创建与程序替换：

```bash
strace -f -qq -e trace=clone,clone3,execve \
  -o /tmp/runc-trace.txt ./anolix run --runtime /usr/sbin/runc \
  --rootfs ./rootfs -- /tprobe
# crun 同样命令，只换 --runtime
```

---

## 数据一：runc 的序列（rootless）

```text
execve("/usr/sbin/runc", ["--root","/tmp/rt-s","run","--bundle",...])
  clone(CLONE_VFORK) = 336684
  execve("/proc/self/fd/6", ["/usr/sbin/runc","init"])     ← re-exec：Go runtime 第 2 次加载
    clone(CLONE_PARENT|SIGCHLD) = 336686
    clone(CLONE_PARENT|SIGCHLD) = 336687
      execve("/tprobe")                                    ← payload
```

两个此前没写进文档的事实：

1. **re-exec 真实发生**：`execve("/proc/self/fd/6", ["runc","init"])`。
2. **double fork 也是真的**：两次 `clone(CLONE_PARENT)`，让容器进程被上层收养，
   而不是挂在 `runc init` 名下。

---

## 数据二：crun 的序列（rootless）

```text
execve(".tools/crun-root/usr/bin/crun", ...)
  clone(CLONE_NEWUSER)                                     ← userns 载体
  clone → execve(newgidmap) ×6（全 ENOENT）                 ← 写 gid_map 的辅助程序
  clone → execve(newuidmap) ×6（全 ENOENT）                 ← 写 uid_map 的辅助程序
  clone → execve(payload)                                  ← 容器进程；setup 在同一份 C 代码里做完
```

数一下进程级 clone：

```text
runc 内部：3 次（re-exec + double fork ×2）
crun 内部：4 次（userns 载体 + 两个 map 辅助 + 容器进程）
```

**crun 的进程更多，却快 2.1×。** 这一条直接打死了"进程数是原因"。

---

## 数据三：zygote 自己的账

09 的 zygote 只测了总时长（4.05 ms），没有分段。分段数据来自 08 的 K=1（7.0 ms），
但那一组是**单样本**，且绝对值比 09 高 3 ms（单样本 + 热身不足；09 是 30 个样本取 p50）。
**所以只用它的比例，不用它的绝对值。**

| 段 | 08 K=1 (ms) | 占该次的比例 |
| --- | ---: | ---: |
| socket + 排队 | 0.30 | 4.3% |
| cgroup | 0.26 | 3.7% |
| **clone** | **0.88** | **12.6%** |
| worker 侧（挂载 + pivot + seccomp + execve + Go runtime） | 5.59 | 79.4% |

按这个比例推算 09 的 4.05 ms：**clone ≈ 0.5 ms**（量级估计，非直接测量）。

而 runc 与 zygote 的差距是 `13.66 − 4.05 = 9.61 ms`：

```text
clone 能解释的上限：~0.5 ms（推算）
实际差距：            9.61 ms
差约 19 倍
```

⚠️ 这个换算的强度有限：比例来自另一批样本、另一个单次。
即使把比例误差算到 2 倍（clone 占 25%），也只有 1 ms，仍然解释不了 9.61 ms。
**结论对比例不敏感，但对“clone 不是大头”这个判断是稳健的。**

---

## 推论：被推翻的是什么

不是"zygote 只 clone 一次"这个事实（它是对的），
而是**把它当成 3.4× 的原因**。

```text
固定成本 = 加载 runtime + 走 OCI 生命周期 + setup

runc   ：2 次 runtime 加载  + 走 + setup
crun   ：1 次 runtime 加载  + 走 + setup
zygote ：0 次 runtime 加载  + 不走 + setup（clone 只是 setup 的第一步）
```

三段差值：

| 区间 | 差值 | 至少包含 |
| --- | ---: | --- |
| runc → crun | 7.15 ms | 少一次 Go runtime 加载；另含 11 MB 与 0.4 MB 二进制的 page-in 差异、更重的 OCI 实现 |
| crun → zygote | 2.46 ms | 不解析 config.json、不写 state、不走 create/start、不加载 runtime |
| 合计 | 9.61 ms | = 3.4× |

clone 不在任何一格里占主要位置。

---

## 边界：新解释同样没有被拆开

必须写清"哪些是确定的、哪些还是假设"，
否则就是用一个新的未验证解释，换掉一个旧的未验证解释。

**已确定（实测）**

- 进程数不是原因：crun 4 个进程 > runc 3 个，却快 2.1×。
- runc 内部确实 re-exec + double fork。
- clone 只占 zygote 自身 12.6%。

**仍是假设（⚠️ 未拆开）**

- runc 的 13.66 ms 里，"加载 runtime"与"OCI 生命周期"各占多少。
- crun 的 6.51 ms 内部怎么分配。
- zygote 与 crun 差的 2.46 ms 具体落在哪一项。

要坐实需要 ftrace 或运行时自身的阶段日志；本机两者都不可用
（runc / crun 都不是为测量设计的）。

---

## 可复用判据

> **如果真是 X 导致的，去掉 X 应该能省多少？**
> 拿这个数去比实际差值——对不上，X 就不是主因。

这次：

```text
X = clone         → 上限 0.5 ms
实际差值          → 9.61 ms
对不上 19 倍      → clone 不是主因
```

同一个判据也可以用在反方向。要证明"cgroup 是主因"：
先算 cgroup 段的量级（6.7 ms），再比"关掉 cgroup 后总时间的变化"
（27.4 → 26.0，只差 1.4 ms）——对不上，说明 cgroup 的时间会被别的等待吸收，
不是净成本。

---

## 教训

1. **分段数据只能说明"这一段占多少"，不能说明"它是原因"。**
   一个占 12.6% 的段，再怎么优化，天花板也只有 12.6%。
2. **一个解释如果没被反面验证过，它就还是假设。**
   这次的反面验证很便宜：数一下对方的进程数。
3. **结构图不要凭记忆画。**
   记忆保存的是简化版（"runc 主进程 + init"），而简化版会把"为什么"一起简化掉。
